# 里程碑「推进意图」与「完成声明」：原逻辑与改后逻辑

> 记录 2026-09-18 ｜ 现象与归因见 `milestone-advance-claim-mismatch.md` ｜ 状态：已改代码，全量测试通过

一句话：用户说「我脑子里过了一遍，就不一一回答你了，直接下一步」，同时表达了两件事——**我完成了**、**往下走**。
原代码把这两件事交给两个互不相通的开关，而这句话只点亮了后者。改后**没有把两个开关合并**（它们是两个真问题），
而是让每个开关都认得出用户在说什么。

---

## 一、原逻辑：勾选那一刻，系统连问了五个问题

触发点只有一个：Agent 调 `update_roadmap(done=True)`（`route.py:782`）。五个问题全部在这一刻、按固定顺序问完，
读的都是**用户上一条回复**。

| 顺序 | 闸 | 它问的问题 | 怎么判 | 判完决定什么 |
|---|---|---|---|---|
| 1 | 闸 1 批量护栏（`route.py:798`） | 是不是已经有里程碑在等用户确认了？ | 确定性，读待确认标记 | 有 → 直接拒绝，一轮只能勾一个 |
| 2 | 闸 2 完成豁免（`route.py:806`） | 用户这句话像不像「我完成了」？ | 确定性，关键词匹配 | 像 → 跳过下面整个验收段 |
| 3 | 闸 3 拒绝节流（`route.py:810`） | 这个回合已经被验收拒过两次了吗？ | 确定性，计数 | 是 → 封锁不再受理（防重试烧光工具预算） |
| 4 | 闸 4 LLM 验收（`route.py:821`） | 对话记录里有没有该里程碑的实质完成证据？ | 语义，独立 LLM 验收员 | 没有 → 驳回，要求先补内容 |
| — | 落盘（`route.py:846`） | — | — | 到这一步，勾选才算真的生效 |
| 5 | 闸 5 推进卡点（`route.py:849`） | 用户这句话像不像「往下走」？ | 确定性，关键词匹配 | 不像 → 设待确认标记，下一轮强制停下询问 |

顺序里藏着最关键的一点：**闸 5 读用户那句话的时候，勾选已经落盘了。**
所以它在逻辑上管不到「该不该勾」，只能管「勾完之后要不要停下来问」。真正决定勾不勾得上的，只有闸 4 的验收员。

## 二、核心矛盾

三个，按因果链排下来。

### 矛盾一：一句话表达两个意思，代码用两份互不重叠的词表各自去猜

完成词表在 `exit_intent.py:68`：学会了、都会了、搞定了、做完了、跑通了、直接勾……
推进词表在 `exit_intent.py:44`：直接下一步、直接进入下一阶段、不用再问……

「直接下一步」只命中后者。用户直觉里这两件事是一体的（"我好了，别问了，往下走"），代码里它们正交——
因为它们**确实是**两个问题："完成了"推不出"授权我继续"。问题不在于分了两个开关，而在于**只有一半的开关听得懂人话**。

### 矛盾二：验收员分不清「谁在宣布」

验收员的规则（`route.py:739`）原来写的是"仅「宣布完成/鼓励/日程性总结」不算"。这条规则的本意是拦 **Agent 的自我声明**——
里程碑验收子系统本身就是被"Agent 没做完就宣布完成"逼出来的（`route.py:728` 的注释记着这段）。

但它顺手把**用户本人的完成宣告**一起否掉了。用户说"我脑子里过了一遍"，在验收员眼里和 Agent 说"我做完了"没有区别。
正因为验收员不认宣告，才需要一条豁免通道（闸 2）；而那条通道是**关键词匹配**——用字符串去还原一个本该由语义判断的区分。
于是通道只能放行会用某几种措辞的人。

### 矛盾三：路线的待办类型，和只看对话的验收机制对不上

路线生成提示词（`route.py:91-92`）同时要求里程碑是"可检验的动作（如本地跑通 hello world）"、又"尽量写成对话内可检验的形式"。
这两句互相拆台：前者天然发生在对话外——"跑通"的那一刻没有第二个人在场；后者要求产出出现在对话里。

更麻烦的是**认知型待办**，例如"能说清 Q4"。它的完成只发生在用户脑子里，而完成词表里全是"跑通/装好/做完"这类带产出的动作词，
自述的措辞一个都不认。结果就是：**唯一能过验收的那扇门，只对会用特定措辞的用户开着。**

### 合起来看

用户那句自然语言，本意是"我好了，别问了，往下走"。系统听到的是"往下走"，然后按规则要求他拿出对话证据；
拿不出来就驳回；Agent 没有别的合法出路，只能回头告诉用户"你补一句能命中关键词的话我就勾"。
一个本该让用户省事的豁免设计，变成了用户要额外做一个动作、去喂系统一个措辞。

## 三、改后逻辑

改动只落在**判定标准**上：没有合并开关，没有动闸门顺序，没有新增闸，也没有放宽验收。

### 3.1 用户在回答里程碑确认时，按他说的分三类走

| 用户说 | Agent 做什么 | 系统怎么判 |
|---|---|---|
| 勾选指令：「直接勾」「勾了吧」 | 调 `update_roadmap` | 闸 2 命中 → 跳过验收，直接勾上 |
| 自述掌握：「我会了」「搞定了」「我脑子里过了一遍」「不一一回答你了」 | 调 `update_roadmap` | 闸 2 命中则直接勾；措辞在词表外时，闸 4 验收员认下用户本人的宣告 → 通过 → 勾上 |
| 只有推进：「直接下一步」「直接进入下一阶段」 | **不调 `update_roadmap`**，直接按指令往下讲，并如实告知「该里程碑我未勾选，后续你可以随时命令我勾选」 | 不产生勾选动作 |

还有第四类，行为保持原样：**用户什么都没说，Agent 自己想勾**——走正常验收，只有对话里的产出算证据。
这一类是验收子系统存在的理由，不动。

分界线值得单独说一句：**第二类和第三类的区别，是"用户有没有说自己掌握了"，不是"用户有没有说下一步"。**
这正是这份设计一开始就写下的规则——该不该勾，看对话里有没有完成证据，而不是看用户有没有说"下一步"。

### 3.2 验收员多了一个维度：谁在宣布

`route.py:739` 的判定规则现在分四句：

- 助手自己宣布完成、鼓励、日程性总结 —— 不算（保留，这是验收存在的理由）
- 布置了任务但没人完成、任务转交但对方没回应 —— 不算
- **用户本人明确表示该项待办自己已完成/已掌握/不必逐条回答 —— 算有效证据，判通过**
- **但用户只表达了"往下走"而没说已掌握 —— 不算完成证据**

最后一句是刻意加的。没有它，验收员会把"直接下一步"过度解读成"学会了"，把第三类重新拽回"勾不上"的老路。
原来那句"宁可误拦，不可放过"也加了例外限定，否则两条规则互相顶。

### 3.3 勾不上时，话术由代码给，不由 Agent 即兴发挥

验收判否时先看用户有没有给推进授权（`route.py:833`）：

- **给了**（用户说了"直接下一步"但没说掌握）→ 返回 `not_checked`，工具结果里直接带着"该里程碑我未勾选，后续你可以随时命令我勾选"这句话，
  并明令不要重试、不要向用户索要措辞、不要解释验收机制。
- **没给** → 走原来的路径：先补内容再勾选。同时补了一句"不要向用户索要『补一句话』式的关键词"。

这条的意义在于：**"勾不上时该说什么"从 Agent 的自由发挥，变成了代码给定的确定性输出。**
即使 Agent 违反了提示词、硬去调了工具，用户看到的也还是同一句话，不会退化成"你再补一句我就勾"。

## 四、同一句话，改前 vs 改后

| 用户说 | 改前 | 改后 |
|---|---|---|
| 「直接勾」 | 跳过验收勾上 → 再问一次是否继续 | **一样**（这一条保持原状） |
| 「我会了」 | 词表只认"学会了/都会了"，不认"我会了" → 跑验收 → 对话里没有产出证据 → 驳回 → 回头找用户 | 认下 → 勾上 → 问一次是否继续 |
| 「直接下一步」 | 验收照跑 → 无证据 → 驳回 → **用户被要求补一句话**（事故现场） | 不勾、直接推进、如实告知未勾选。用户零额外动作 |
| 「我脑子里过了一遍，就不一一回答你了，直接下一步」 | 同上，且反驳两次还会触发节流，整回合报废 | 免验收勾上 + 免确认直接推进，全通 |

## 五、这次解决了什么、没解决什么

**解决了**

1. **用户被要求"补一句话喂关键词"**。这句话术不再由 Agent 即兴组织，也不再向用户暴露验收机制；第三类场景下用户根本不会被追问。
2. **认知型待办的完成有了证据形态**。用户自述（"过了一遍""不一一回答"）被认下——这类待办本来就只能在脑子里完成，不认自述等于它永远无法闭环。
3. **验收员不再把用户的宣告和模型的自夸一锅端**。区分"谁在宣布"回到了它该在的地方：语义判断，而不是关键词匹配。

**没解决（已知边界）**

1. **第三类"不调工具"是提示词约束，不是代码保证。**代码只在 Agent 调了工具时才能给出确定性话术。
   如果 Agent 既不调、也没照提示词说那句告知，用户只是看不到状态，并不会被打扰——不会退化成事故，但也拿不到那句说明。
2. **进度会漂移。**用户一路"直接下一步"走下去，里程碑就一直挂着不勾。告知话术里留了"随时可以命令我勾选"的口子，但没有自动兜底。
3. **闸 1 的护栏强度取决于用户措辞。**用户给了推进授权时闸 5 不设卡点，闸 1 也就不拦，同一轮里可以连勾多个里程碑。
   评估后决定不动：闸 2 只认完成措辞、不认推进措辞，所以连勾的每一个里程碑仍然要各自过验收、或各自带完成声明，风险已经被闸 4 盖住。
   若改成"本回合勾选计数"来解耦，反而会在授权场景下把第二个里程碑挡掉，而它给出的错误消息（"请先等用户确认后再勾选下一个"）
   在那个场景下是假的——没有待确认的事。
