# 里程碑「推进意图」与「完成声明」的语义错配

> 记录 2026-09-16 ｜ 范围：`src/domain/exit_intent.py`、`src/pipelines/route.py` ｜ 状态：仅分析，未改代码
>
> **后续（2026-09-18）**：已按本文归因实施改动，原逻辑/改后逻辑对照见 `milestone-advance-claim-fix.md`。
> 第六节列的两种改法里，**选项一采纳了一半**——"点破 advance 只免确认不免验收"作为防线保留，但真凶不在提示词，
> 所以它只是补丁不是解药；**选项二否决**——让 advance 参与豁免判定（无论放行还是拦截）都是拿"推进授权"去回答
> "完成了吗"，与第二节自己写下的规则冲突。真正的修法落在验收员规则、驳回话术和完成词表三处。

一句话：用户说「直接下一步」是一个复合意图（我完成了 + 往下走），但代码把它拆成两个正交开关
`is_completion_claim`（完成声明 → 豁免验收）和 `is_advance_directive`（推进授权 → 免确认），
且两者的关键词集**不重叠**。用户那句自然语言只命中了后者，于是验收照跑、脑内完成无证据、
被驳回——最终表现为 Agent 反过来向用户讨要一句能命中关键词的话才肯勾选。

---

## 一、现象

用户回答里程碑确认时说：

> 我脑子里过了一遍，就不一一回答你了，直接下一步

Agent 的回复：

> 行，继续往前推。但 s1-m1 我先不勾——那条待办要的是「你能说清」，你脑子里过了但没有痕迹，
> 系统核对不到，勾了也会被驳回。你哪会儿方便补一句话（比如就回答 Q4 说「不会进上下文，因为没命中
> 就不读正文」），我立刻勾上。这不挡进度，1.2 照常开讲。

用户本意是「省事跳过」，结果被反问「再补一句话」。体验上的别扭在于：一个想要"直接往下"的请求，
被系统反过来要求多做一步，而这多出来的一步不是为了学习，是为了喂给系统一个能命中关键词的措辞。

---

## 二、两个函数的职责与触发位置（代码依据）

两个函数都**不是**被用户输入直接触发，而是只在 `update_roadmap` 工具被调用、且 `done=True`
（勾选里程碑）时，去读用户**上一条回复**（`_recent_user_text`，route.py:712）做两个正交判定：

| 函数 | 调用位置 | 作用时机 | 决定什么 | 关键词集 |
|---|---|---|---|---|
| `is_completion_claim` | route.py:798（闸 2） | 勾选**之前** | 是否**跳过 LLM 验收** | 学会了/搞定了/做完了/跑通了/直接勾/跳过吧… |
| `is_advance_directive` | route.py:833（闸 5） | 勾选**之后** | 是否**免确认推进**（不设 pending 卡点） | 直接进入下一阶段/直接推进/不用再问… |

`_update_roadmap`（route.py:772-843）的闸门顺序：

1. 闸 1（790）：批量护栏——已有待确认里程碑时拒绝，一轮只能勾一个。
2. 闸 2（798）：`verify_enabled = ROUTE_MILESTONE_VERIFY and not is_completion_claim(latest_user)`
3. 闸 3（804）：拒绝节流——本回合被验收拒绝 ≥2 次不再受理。
4. 闸 4（813）：LLM 验收 `verify_milestone`（只看「里程碑标准 + 对话记录」，无 evidence 注入通道）。
5. 闸 5（833）：`if not is_advance_directive(latest_user): 设 coach_milestone_pending` → 提示词强制停下总结+询问。

关键在**顺序**：`is_advance_directive` 被读的那一刻（833 行），勾选**已经成功**（已过闸 4 验收、
已 `save_roadmap`）。所以它在逻辑上不可能反过来成为"该不该勾"的理由——它压根不在勾选之前运行。
真正决定"该不该勾"的只有闸 4 的验收员，而验收员只认**对话证据**，不认用户措辞。

因此结论是：**该不该勾 = 对话里有没有完成证据，而不是用户有没有说"下一步"。**

## 三、四层矛盾（按因果链）

### 矛盾一：一个意图，两个开关，词集不重叠

「直接下一步」逐条跑正则：

- `is_completion_claim` = **False**：整句没有「学会了/搞定了/直接勾/跳过吧」等词，命不中。
- `is_advance_directive` = **True**：`直接` + `下一步` 命中 `_ADVANCE_RE` 第一分支。

用户以为这两件事等价（都是"我好了，别问了，往下走"），但代码里一把管"要不要验证据"、
一把管"勾上后要不要问你"。自然语言用同一句话同时表达，却只点亮了后者。

### 矛盾二：待办性质与验收机制错配

s1-m1 的待办是「你能说清 Q4」，它的完成发生在**用户脑子里**。而验收员（`verify_milestone`）
只能读**对话文本**，看不到脑内状态。用户说"我脑子里过了一遍"，在用户视角确实完成了；
在系统视角，这句话不含任何可核对的实质内容，等于零证据。

这个鸿沟 `exit_intent.py` 的注释其实承认了："里程碑常在对话外完成（如本地跑通 hello world
在 IDE 里），对话中天然无证据"——所以才设计了 claim 豁免通道。但（见矛盾一）用户这次没用
claim 的措辞，豁免通道闲置，硬验收上线。

### 矛盾三：提示词怂恿 vs 验收驳回，Agent 被夹

- route.py:151 提示词怂恿："用户上一轮已明确指令『直接进入下一步/不用再问』时，勾选后直接推进"。
- 闸 4 验收员驳回：claim 未命中 → 验收照跑 → 对话无证据 → **必 reject**。

Agent 被两股力夹住：硬勾 → 被 reject（烧工具预算，连续两次还会触发闸 3 拒绝节流，整回合报废）；
不勾 → 就得向用户解释。它选了后者。

### 矛盾四：Agent 把系统的验收成本转嫁给用户

Agent 没有别的合法出路，只能把 claim 豁免的**触发条件**反过来告诉用户——"你补一句话（能命中
『学会了/搞定了』的措辞），我就有凭证了，立刻勾上"。于是本该让用户"说一句就跳过"的豁免设计，
变成了**用户被迫多做一个动作去喂系统一个关键词**。这是那句回答里最伤体验的部分。

## 五、根因定位（两个上游点）

其余矛盾都是这两个上游点的下游连锁：

1. **`exit_intent.py` 词集不重叠**：claim 与 advance 的关键词集没有交集，用户表达"完成 + 推进"
   的自然措辞（"直接下一步"）进不了 claim。`is_completion_claim` 的取词严格是有意的——注释写明
   "误豁免代价 = 少验一次"，所以收紧了词表；但代价是口语化的完成表达大量漏判。
2. **`route.py:151` 提示词把"下一步"和"勾选"绑在一起**：那句"勾选后直接推进"描述的是勾选**之后**
   的行为，却让 Agent（和人）读出了"下一步 = 该勾"的暗示。措辞把一个"勾选后"的开关，暗示成了一个
   "勾选前"的动作。

## 六、现状与待决

本次只做现象记录与矛盾归因，**未改任何代码**。两个可选改法，各有代价，尚未决定：

- **改提示词（route.py:151）**：把"advance 只免确认、不免验收；证据不足仍会被驳回"点破，
  消除 Agent "下一步 = 该勾"的错觉。改动小、不碰闸门逻辑，但根因（词集不重叠）仍在。
- **改闸 2（route.py:798）**：让 `is_advance_directive` 也参与豁免判定。代价是用户烦躁时一句
  "直接下一步"就能跳过验收，与"宁可误拦，不可放过"的设计初衷相悖，不推荐。

判定规则一句话（可同时对齐人和 Agent）：**勾选前只问一件事——这个里程碑的完成证据，现在已经在
对话里了吗？在 → 勾；不在 → 不勾，先补证据。"下一步"只影响勾上之后要不要再问，不影响勾不勾得上。**
