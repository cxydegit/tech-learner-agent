# 自建 ReAct Loop vs 当前确定性管道 + LangGraph 图编排

> 一句话结论：
>
> **核心功能（collect / read / note）为什么用「确定性管道 + LangGraph 图编排」而不是「让模型自主编排工具」？**
> 同一批任务基准测试显示：agentic ReAct 循环成功率波动大、token 成本高一个量级、LLM 调用次数随循环累积；
> 确定性管道接近 100% 成功、每个任务只做一次 LLM 生成、token 成本可控。**LangGraph 的价值不在「单任务跑得快」，
> 而在「有状态、可中断、跨会话」的编排能力** —— 这正是 `/learn` 会话需要它、而单次 collect/read/note 不需要它的原因。

---

## 1. 背景：这个对比回答什么问题

项目从 MVP（ReAct Agent 自主编排工具）演进到「确定性管道 + 图编排」，核心叙事是：
**线性流程（资料收集 / 文档解读 / 笔记沉淀）用确定性管道，开放流程（多轮学习会话）才用 agentic。**
但此前这一判断主要来自开发过程中的踩坑记录，缺少一份**同任务、可复现的数据支撑**。

本 benchmark 补上这块数据：同一批 collect 任务，两种实现各跑 N 次，对比
**成功率 / 耗时 / 工具调用数 / LLM 调用数 / token 成本**。

## 2. 对比矩阵：agentic ReAct Loop vs 确定性管道 + 图编排

| 维度 | 自建 ReAct Loop（agentic） | 确定性管道 + LangGraph 图编排 |
|------|----------------------------|-------------------------------|
| **编排者** | 模型自主决策工具序列（search → fetch → ... → 结束） | 代码编排工具序列；模型只做**单次**生成 |
| **工具调用** | 由模型决定，可能重复/误用/漏用 | 固定且可预期：搜索×3 → 抓取≤5 → 保存×1 |
| **LLM 调用次数** | 循环轮数（数轮 ~ 十几轮） | 每任务 1 次 |
| **对话历史** | 每轮累加全量历史，token 随轮数**指数摊大** | 单条请求，无循环历史 |
| **token 成本** | 高（多轮 × 递增历史） | 低（单次生成） |
| **成功率** | 依赖模型持续遵循 ReAct 格式，格式漂移 / 超时 / 幻觉「已保存」是固有失败模式 | 近 100%（唯一失败源是外部 API 网络异常） |
| **失败模式** | 文本解析脆弱、工具参数截断、模型编造结果 | 主要是搜索/抓取网络失败，可重试、可降级 |
| **状态管理** | 进程内对话，无持久化、不可中断恢复 | LangGraph 状态 + SqliteSaver 跨会话恢复 + `interrupt()` 人机交互 |
| **可观测性** | 文本循环难追踪单步 | 节点化、可流式、checkpoint 任意回放 |
| **生产定位** | 冻结的 benchmark 基线（`baselines/react_agent.py`，主流程不 import） | 主流程（`src/graph.py` + `src/pipelines/`） |

## 3. 基准测试方法

- **同任务**：同一批 collect 任务（技术名），两种实现各跑 N 次（默认 2 任务 × 2 次 × 2 侧）。
- **指标**：成功率 / 耗时（wall-clock）/ 工具调用数 / LLM 调用数 / token 成本（输入 + 输出，`usage` 累计）。
- **成功率判定**（两侧同一规则、纯规则、无额外 LLM 调用）：
  产物 = graph 侧 collect 报告文本 / agent 侧 Final Answer 文本；
  成功 = 产物非空 **且** 含 ≥ 2 个 http(s) 链接。
- **公平性说明**：agent 侧任务描述写进 user 输入、由模型自主完成；graph 侧走生产 `collect_pipeline`
  （代码编排 + 单次 LLM 合成）。两侧目标产物相同，差异即「让模型自主编排」vs「代码编排」的架构差异。
- **插桩**：不改动源码。LLM/token 通过包裹 openai SDK `chat.completions.create` 累计；
  工具调用 agent 侧在 `execute_tool` 唯一入口计数、graph 侧在 `pipelines/collect` 的 search/save 与
  `adapters/fetch` 的 `fetch_tool` 处计数（并发批 `fetch_many` 内部逐个调它，仍按 URL 计）。

## 4. 基准测试结果

下表为正式档（2 任务 × 8 次 × 2 侧，`--trials 8`，每侧 16 次），graph 列基于**并发抓取后**的实现（2026-08-14 实测）。
运行脚本未随仓库分发，以下为当时的历史记录；指标口径见 §3。

| 合计指标（16 次/侧） | agentic ReAct Loop | 确定性管道 + 图编排 | 观察 |
|----------|--------------------|--------------------|------|
| 成功率 | 100%（16/16） | 100%（16/16） | 简单任务下两侧无差异（见 5.3 局限） |
| 平均 LLM 调用 | 3.3（单次 2~6） | 1.0 | agent 循环累积历史 |
| **平均 prompt token** | **15,734** | **5,898** | **agent 高 ~2.7 倍**（极差 5.6k~58k vs 9.6k~11.1k） |
| 平均工具调用 | 2.2（1~4） | 8.9（固定 9） | agent 少抓取、链接未逐页验证 |
| 平均耗时（均值/中位） | 86.3s / 47.4s | 76.9s / 69.8s | 并发后基本打平；agent 有 704s 长尾、graph 238s |

## 5. 数字背后的判断

1. **token 成本是确定性管道最硬、且被数据证实的优势**：agent 循环每轮把全量对话喂回模型，prompt token
   平均是确定性的 ~2.7 倍（15,734 vs 5,898），且极差极大（最高 5.8 万 vs 确定性最高 1.1 万）；
   确定性管道每任务 1 次 LLM 调用，成本**可预算**。
2. **耗时在并发抓取后基本打平，且确定性侧一致性更好**：均值 graph 76.9s / agent 86.3s、中位 69.8s / 47.4s。
   agent 中位更快（它少做验证），但存在一个 **704s 的致命长尾**（某次循环失控）；graph 的长尾（238s）来自慢抓取。
   并发化已把「确定性慢 3x」这个实现细节的产物消除（详见 5.2）。
3. **成功率两侧都是 100%（N=16）——本 benchmark 没能量化「可靠性差距」**：任务是刻意选的——
   故意选「不依赖打大段内容」的简单任务，正好避开了 agent 的已知弱点。所以「可靠性」结论要诚实地下限：
   **本数据支撑的是成本与一致性优势**；agent 在需写大段内容任务上的失败模式，由第 6 点的
   内容质量实证记录支撑，而非本数据集（详见 5.3）。
4. **LangGraph 的价值不在单任务性能**：同样的 loop 换 LangGraph 编排，单次任务不会更快更省 token ——
   框架的杠杆在**状态管理**：checkpoint 跨会话恢复、`interrupt()` 人机确认、节点化可观测性。
   这就是「单次 collect 不需要 LangGraph，而 `/learn` 会话需要」的原因。
5. **这是「分层设计」而不是「放弃 Agent」**：线性流程用确定性管道（token 可控、内容可验证），
   开放/回溯/human-in-the-loop 流程用 agentic。数据支撑了「什么时候该用 / 不该用 Agent」这个判断。
6. **内容质量不可控，是 agentic 最隐性也最难量化的成本**。同一任务（FastAPI collect）实测对比：
   - 确定性报告：来源清一色高质量（官方文档 / 官方模板），带正文级细节（`uv run fastapi dev`、`/docs` Swagger、
     Docker Compose），末尾诚实标注「已排除 2 条低质量链接」——因为喂给 LLM 的是 `screen_results` 预筛后
     top-5 页面的**正文**。
   - agent 回答：混入未过筛渠道（菜鸟教程、W3CSchool、CSDN、B 站视频），且出现**编造的坏链接**
     （`https://blog.csdn.net/.../article/details/...` 以字面 `...` 结尾）。一次 fetch 只返回一页，而回答有
     8+ 链接，未抓取的链接只能从搜索摘要（标题 + 200 字 snippet）抄，简介自然靠猜。
   - 根因：agent 抓不抓、抓几个由模型当天状态决定（实测 0~3 次），grounding 深度是**抽样方差**；
     确定性管道把「预筛 + 抓 top-5 正文」写成固定策略，质量是**代码保证**而非模型心情。

### 5.2 抓取数量的取舍（为什么默认 5，要不要减）

- **耗时去哪了**：5 次 Firecrawl 请求**顺序**排队，是 3 分钟均耗时的主因（FastAPI 96s / Spring Boot 266s 的差别
  基本就是被抓页面的网络延迟）。抓取本身是「质量换速度」——多读正文，LLM 才能写准简介、排对优先级。
- **5 是不是太多**：从 FastAPI 报告看，核心必读 4 项全部来自 top-4 官方文档（一次抓取覆盖一个），第 5 个抓取
  （第三方教程）只贡献了扩展阅读，边际价值明显递减。**3~4 次通常已够核心 grounding**。
- **真正的杠杆是并发，不是减数量**：Firecrawl 延迟是网络瓶颈，5 次**并行**抓取可把耗时压到 ~1/4，
  且**不影响 grounding 质量**；减到 3 只省 ~40% 且牺牲深度。
- **已实现**：`collect` 改为并发抓取——`adapters/fetch.py::fetch_many`
  线程池并行 + 按输入顺序归并（保持确定性）+ 共享 deadline 封顶墙钟，单次超时记空结果不拖垮整批；
  默认 `FETCH_MAX_WORKERS=5`、`FETCH_TIMEOUT_SECONDS=45`（config 可调），`MAX_FETCH_PAGES` 保持 5。
- **对 benchmark 的影响（已实测，正式档 N=8）**：并发后 graph 侧平均耗时降到 **76.9s**（与 agent 86.3s
  基本打平；中位 69.8s vs 47.4s），长尾从 293s 收窄到 238s。token 成本（~2.7x prompt）与 LLM 调用次数
  （1 vs 3.3）的优势是**架构性的**，不受影响。结论：**耗时差距是顺序抓取这个实现细节的产物，
  不是确定性架构的固有属性**。

### 5.3 为什么成功率两侧都是 100%（本 benchmark 的边界）

- **任务选择是设计好的**：benchmark 刻意用「不依赖打大段内容」的简单任务
  （如搜索并返回链接），避免基线在已知弱点上必挂。结果就是这批任务 agent 也稳定成功——
  **「可靠性差距」不在本数据集的射程内，必须如实说**。
- **这不削弱可量化的结论**：token（~2.7x，极差 5 倍）、LLM 调用（3.3 vs 1）、工具调用不可预期、
  704s 长尾，加上第 6 点的内容质量实证（编造的坏链接、未过筛内容农场），已构成「确定性管道更可控」的论据。
- **要量化可靠性差距，需换任务集**：把「把整份 Markdown 报告写进文件」这类含大段工具参数的任务加进
  benchmark，agent 侧成功率会显著下降——但那是另一个 benchmark（带预设结论的风险）。本项目目标是用数据
  支撑「token / 一致性 / 内容可验证」这几点，已达成；可靠性的证据走内容实证的定性路径。

## 6. 什么时候该用 agentic（来自本项目的判断）

任务**开放**、工具序列**不可预知**、需要**回溯 / 重试 / human-in-the-loop** 时才用 agentic；
固定步骤的线性任务用确定性管道更可靠、更便宜。判断标准是「模型的自主决策是否真的带来增量价值」，
而不是「能不能用 Agent」。

## 7. 结论

- **可预算性**：确定性管道每任务 1 次 LLM 调用、prompt token 约为 agent 的 1/2.7；agent 的成本随循环轮数累积，且极差大（5.6k~58k vs 9.6k~11.1k）。
- **可验证性**：确定性管道预筛后抓 top-5 正文，链路逐条可溯源；agent 抓不抓、抓几个由模型当天状态决定（实测 0~3 次），grounding 深度是抽样方差。
- **可预期性**：工具序列固定（搜索×3 → 抓取≤5 → 保存×1），失败源收敛到外部 API 网络异常，可重试、可降级。
- **耗时**：并发抓取后两侧基本打平——耗时差距是顺序抓取这个实现细节的产物，不是确定性架构的固有属性。
- **框架的杠杆**：LangGraph 的价值不在单任务性能，而在状态管理（跨会话恢复、`interrupt()` 人机确认、节点化可观测性）。这是单次 collect 不需要它、而 `/learn` 会话需要它的原因。

一句话：**单任务性能不是框架的战场，可预算性与可编排性才是。**
