# 笔记合并（去重）功能优化报告

> 对应 RAG_OPTIMIZATION P0 去重部分：从「确定性规则确认层」到「LLM 判定 + 用户确认」的完整演进记录。
> 结论先行：**确定性表面特征做不了「同义改写识别」；灰色区必须上 LLM 判定，用户确认兜底。**
> 手写黄金集的"100%"是出题人偏置的产物，不代表真实准确率。

---

## 一、背景：优化前的问题

`note_pipeline` 提取新知识点后要与已有笔记去重合并。旧逻辑（`_find_dedup_match`）以
语义相似度阈值 `RAG_DEDUP_THRESHOLD`(0.55) 为合并依据，出现两类问题：

1. **高相似但无关的误合并**：Redis 主题的笔记之间互相相似 0.62~0.66（同一领域语义空间
   天然聚集），0.55 阈值把无关笔记全并到一起——实证：「Docker 部署 Redis 集群」因共享
   标签 #部署 误并入 windows 环境笔记。
2. **字面零重叠的同义改写无法合并**：同知识点换一套措辞后，字符串特征全变，阈值匹配不到。

第一版方案（P0）把「候选召回」和「合并决策」解耦：Embedding 只管召回 top2（不牺牲召回），
是否同一知识点由**确定性确认层**验明正身——标题 overlap / 具体标签 overlap / 内容判别性
概念 containment，任一确认即合并。在**手写黄金集**（12 条）上表现 100% 精确率 / 0 误合并。

## 二、压力测试：100% 是假象

手写黄金集是「我出题、我答题」的产物：样本由自己挑、预期由自己定，存在**作者偏置**。
为测出真实准确率，用 LLM 合成压力测试（生成者 ≠ 标注者，规则程序化标注）：

- **同义改写** ×每篇 4：同一知识点、措辞完全不同（标题+正文）→ 应合并
- **近邻干扰** ×每领域 4：相邻但不同的主题 → 不应合并

生成 55 条（同义改写 47 / 近邻干扰 8），对每篇真实笔记生成、标题与源重叠的样本丢弃
（避免测试退化成标题匹配）。结果（旧确认层）：

| 指标 | 数值 | 分布 |
|---|---|---|
| 合并精确率 | **21%** | 正确合并 4 / 错合并 12 / 误合并 3 |
| 合并召回率 | **9%** | 正确合并 4 / 漏合并 31 |
| 误合并率 | **38%** | 8 条近邻干扰中误并 3 |
| 漏合并率 | **66%** | 47 条改写中漏并 31 |

### 根因隔离：瓶颈在确认层，不在召回

对 47 条改写做**信号隔离分析**——假设源笔记就是候选（Embedding 完美召回），只算
确认层的三个确定性信号：

```
标题确认 0 / 标签确认 4 / 内容确认 0 / 三信号任一确认 4（9%），全不确认 43（91%）
```

三个致命真相：

1. **内容 containment 信号对「真正措辞不同」的改写确认率 0/47**。它要求改写里的
   判别性概念**逐字出现**在源笔记正文——真正重写的内容词汇全换了，一条都救不回来。
   手写黄金集里内容信号"有效"，是因为我写的用例复述了源笔记措辞（无意偏置），
   是**假阳性**，不是真能力。
2. **标签信号（4/47）还会撞到错误候选**，造成错合并——「NoSQL内存数据库五种核心角色」
   被标题 overlap 命中「redis 的五大核心角色」：旧 `_topics_overlap` 中文**单字切分** +
   `max(占比) ≥ 0.4`，一个"五"字就能让两个标题"共享 40% 词元"。
3. **相似度本身分不开**：同义改写对源笔记 0.50~0.75，近邻干扰也有 0.60~0.63——
   分布重叠，任何阈值都无法同时压低误合并与漏合并（这解释了最初 0.55 问题的本质）。

## 三、新方案：标题 fast-path + LLM 判定 + 用户确认

```
新笔记 (title, tags, content)
  │
  ▼
① 候选召回：Embedding 语义 top2（同 tech，不变）
  │     相似度 < RAG_DEDUP_JUDGE_SIM_MIN(0.4) 的候选不送判定（省 LLM 调用）
  ▼
② 标题 fast-path：去停用词后标题词元**完全相等**（"标题基本同一句"）
  ├─ 是 → 标 same（标题等同），跳过 LLM，直接进 ④
  └─ 否 → ③ LLM 判定每对 (新笔记, 候选)
              LLM 输入：双方 标题 + 标签 + 正文（前 2000 字）
              LLM 输出：{"verdict": "same"|"diff", "reason": "一句话理由"}
              失败/解析异常 → 安全侧判 diff（不合并）
  ▼
④ "same" 候选 → merge_candidates 展示（附理由）→ 用户确认合并进哪篇 / 拒绝
   "diff"（全部）→ 直接写新笔记（无 match 不问，与现状一致）
```

设计要点：

- **分层定位**：标题 fast-path 只「省一次 LLM 调用」，不决定合并；LLM 判定是**建议**
  不是决定；**用户确认是最终闸门**——错误的判定最坏后果是用户多看到一个候选，
  不会静默污染知识库。
- **标题 fast-path 阈值**：去停用词（数词/量词/meta 后缀词：机制/原理/详解/对比…）后
  词元集合**完全相等**。刻意不设"重合度 ≥ 0.6"宽松档——「缓存穿透与缓存雪崩」vs
  「缓存雪崩」重合 2/3 但主题不同，灰色区留给 LLM。
- **判定粒度**：按**主题**聚合而非知识点分离——同一主题下不同子问题（缓存穿透 vs
  缓存雪崩）判 same 合并；只有「看起来相似但讲的完全不是同一件事」才判 diff
  （对齐知识库按主题组织笔记的习惯，避免判定过严放大 LLM 幻觉）。
- **删除的旧逻辑**：`_same_knowledge_point` 确认层整体删除（`_tag_overlap`、
  `_content_concept_overlap`、`_discriminative_concepts`、`_TAG_STOP`/`_CJK_STOP`/
  `_LATIN_STOP`、`RAG_DEDUP_THRESHOLD`、`RAG_DEDUP_CONTENT_THRESHOLD`）。

改动文件：`domain/dedup.py`（fast-path 纯函数 + 单测）、`adapters/llm.py`
（判定 prompt + `judge_same_knowledge_point`）、`adapters/store.py`（`find_note_match`
重构，返回 (match, sim, reason)）、`pipelines/note.py`（merge_candidates 带理由展示）、
`config.py`（`RAG_DEDUP_JUDGE_SIM_MIN`）、`domain/extraction.py`（`parse_json_object`）、
评估脚本（评估适配 + 理由列）、`tests/test_dedup.py`。

## 四、评估结果：同一合成集复测

| 指标 | 旧（确定性确认层） | 新（fast-path + LLM 判定） | 变化 |
|---|---|---|---|
| 合并精确率 | 21% | **77%** | +56pp |
| 合并召回率 | 9% | **70%** | +61pp |
| 误合并率 | 38% | **12%** | -26pp |
| 漏合并率 | 66% | **11%** | -55pp |
| 分布 | 正并4/正不并5/错并12/误并3/漏并31 | **正并33/正不并7/错并9/误并1/漏并5** | — |

### 剩余 15 个非正确项的性质

- **漏合并 5（11%）**：其中 4 条相似度为"—"——**召回层瓶颈**（改写与源笔记 embedding
  相似度 <0.4 或没进 top2，未送到 LLM）。这不是判定问题，是 Embedding 的固有边界。
- **误合并 1（12%）**：GraphRAG → rag 检索增强生成。主题粒度下 LLM 判"同属 RAG 主题"
  ——标准分歧（golden 按知识点标注），且用户确认会拦。
- **错合并 9**：LLM 判 same 但目标笔记选错（同主题家族多篇相近笔记时的选目标问题），
  全部在用户确认的拦截范围内。

### 概念澄清：合并召回率 ≠ Embedding 召回

「合并召回率」是样本走完**整条流水线**的通过率，横跨召回层与决策层。本次提升
**不是** Embedding 变强（候选召回层一行没改），而是决策层换人：

```
信号隔离实验证明：91% 的改写即使被 Embedding 送到面前，旧确认层也不放行
→ 旧 66% 漏合并的主体是「决策层毙掉召回结果」，不是「Embedding 没召回」
→ 新方案的 5 个漏合并才是真正的 Embedding 瓶颈
```

即：**重构把瓶颈从「决策层」（可修，已修）逼到了「召回层」（Embedding 固有边界）**。

## 五、结论与后续方向

1. **确定性规则做不了语义等价判断**——「是否同一主题」是 LLM 的强项，灰色区交给
   LLM 判定，用户确认兜底，是当前知识库规模下的正确分工。
2. **手写黄金集不能当真实准确率**——评估必须生成者 ≠ 标注者（合成压力测试），
   且 N=12 的"100%"即使为真也有 ~25% 的置信上限（rule of three）。
3. 后续可选项（当前非主要矛盾）：
   - 调低 `RAG_DEDUP_JUDGE_SIM_MIN`（0.4 → 0.35）救回部分召回层漏合并（代价：更多候选
     送 LLM、更多错合并机会）；
   - 错合并的候选择优：LLM 一次看 top2 输出「最佳匹配 or none」，替代「第一个 same 就返回」；
   - 召回层升级方向：**P1 混合检索已实测排除**（见下），P4 非对称 embedding 未实测、仍开放。

### 附：P1 混合检索搭入去重召回的评估（已实测，结论：不搭）

> 结论：**可以但没必要——净提升为零，且引入排序噪声与相似度语义破坏。**

对 47 条改写样本实测「源笔记进语义 top2 vs 混合 top2」（探针脚本，零代码改动）：

| 指标 | dense | hybrid（BM25 + RRF） |
|---|---|---|
| 源笔记进 top2 | 34/47 | **34/47（无净变化）** |
| 5 条漏并中可救回 | — | 仅 1 条（dense r0 → hybrid r1，dense_sim 0.44） |

三个原因：

1. **补的短板不对口**：混合检索补 dense 丢「精确词匹配」（QA 用户搜 FT.SEARCH/RedisJSON
   等专有名词）；去重缺的是「发散改写」——改写刻意换掉措辞，BM25 词法同样无匹配，
   反而把恰好共享 "Redis" 等泛词的无关笔记打进 top2（排序噪声）。
2. **8 条当前正确并的样本会被挤出**：探针显示 8 条改写（微软视窗宿主…、复杂自主程序构建、
   多层级智能执行架构、LLM 私有化部署、Redis 近似估算方法等）的源笔记 dense r1 → hybrid
   r3/r4 甚至 top5 外——hybrid 换回正确排序的收益会被这批新漏并抵消（净零的由来）。
3. **额外代价**：hybrid 的 `similarity` 是 RRF 归一化分（top=1.0）而非余弦，破坏
   `find_note_match` 的 `sim ≥ 0.4` 下限语义（需改用 `dense_similarity`，且非 dense 候选
   该字段为 None）；BM25 每次去重全量内存打分，库大后是开销。

**结论**：混合检索的用武之地在 QA（专有名词检索），去重的失败模式（发散改写）恰是它的
盲区。提升召回应优先考虑降 sim 下限或 `top_k=2→3`（LLM 多看一个候选）。
