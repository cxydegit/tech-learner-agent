# 场景检索评估 v1.5：取件口径按笔记去重（/ask 与 coach 注入）

> 版本脉络：v1.0 纯评估 → v1.1 分词 + coach 门槛 → v1.2 修正诊断 + 零分填充修复 → v1.3 词法软重排 → v1.4 集子扩充（56→72 条）+ 评测改跑生产函数 → **v1.5 取件口径（把 v1.4 发现的「名额单位」修掉）**。
> 数据说明：评测脚本与黄金集未随仓库分发，下表为实测记录；**「期望笔记」列已匿名化**——原为个人知识库的文件路径。
> 运行时间：2026-10-07 ｜ 检索器：hybrid（= 生产默认）。before 侧是同日同索引的基线快照。

## 一句话结论

1. v1.4 发现的「**名额单位**」问题已在生产里修掉：`/ask` 与 coach 注入的取件口径从「取 N **条分块**」改成「取更多分块 → **按笔记去重** → 截断到 N **篇**」。
2. 同口径 before/after：多篇联想（cross_note）的 `/ask` 取件召回 **79% → 83%**（按篇 17/21 → 18/21）；coach 注入召回 **93% → 93%**（不变），注入的笔记从 18 篇变 21 篇。
3. **归因干净**：改的是取件口径，**排名一条都没动**——72 条查询的「前 top-k 条分块去重序」与基线逐条比较 **0 条变化**，检索层汇总指标（hit-rate / MRR / recall / precision）与基线逐位相同。
4. **预期偏差（诚实记录）**：v1.4 预估 cross_note 召回「79% → 约 86%」，实测 83%。差在**下一个瓶颈不是召回深度而是取件上限**：4 篇期望笔记已经落在召回里，却被「只交付 5 篇」切掉，位次分别是第 8、第 8、第 9、第 12 篇。同一批召回的**上限反事实**（下表）显示：上限放到 8 篇 → 90%，放到 12 篇 → 100%。

## 口径与环境

| 项 | 值 |
|---|---|
| 集子 | 72 条（exact 20 / semantic 15 / cross_note 8 / fuzzy 14 / discriminative 8 / negative 7） |
| embedding 模型 | `text-embedding-v3` ｜ chunker v3 ｜ 索引 884 个分块 ｜ 知识库 64 篇笔记 |
| 召回深度 | 24 条**分块**（= 旧口径候选池的深度：旧代码本来就算出 24 条，只是丢弃了后 16 条） |
| 交付上限 | `/ask` ≤ 5 **篇**（每篇 ≤3 段 × 500 字）｜ coach 注入 ≤ 3 **篇**（每篇 1 段 × 500 字） |
| 聚合口径 | 「按题平均」= 每题召回率的算术平均；「按篇汇总」= 命中期望笔记总数 ÷ 期望笔记总数 |
| 代码版本 | git `1bb0aa5`（改动前）→ 本次改动（未提交） |

## 改了什么（生产侧，确定性）

| 位置 | 旧 | 新 |
|---|---|---|
| `/ask` 召回 | 取 8 条分块 → 按笔记分组（≤5 组） | 取 24 条分块 → 按笔记分组（≤5 组） |
| coach 注入 | 取 8 条分块 → 过闸 → 取前 3 **条** | 取 24 条分块 → 过闸 → **每篇取最靠前的一条**，取前 3 **篇** |
| 候选池 | 由 `top_k` 推导 `max(top_k×3, 8)` = 24 | 显式取「召回深度同值」= 24（同池同序，**不改排名**） |
| 配置 | `QA_TOP_K = 8`（含"召回条数"语义） | `QA_RECALL_CHUNKS = 24`（召回分块数）+ 交付上限独立成篇数口径 |

**为什么取 24**：旧口径的候选池本来就是 24 条（`max(8×3, 8)`），生产只用前 8 条。取满池子 = 索引一次算出的候选全部用上，**不增加任何检索成本**（每条查询仍是 1 次 embedding 调用），且因为池子不变，排名与旧口径逐条相同——before/after 的差异 100% 来自取件口径。

**上下文预算未增**：`/ask` 段数上限仍是 5 篇 × 3 段 × 500 字 = 7500 字；coach 仍是 3 × 500 = 1500 字。材料上限不变，只是同样体积下装的是**不同笔记**而不是同一篇的重复分块。

## before/after

| 环节 | 条目 | 期望笔记 | before | after | 赢 / 输 / 平 |
|---|--:|--:|--:|--:|--:|
| `/ask` 取件（cross_note） | 8 | 21 篇 | 79%（按题）｜17/21 | **83%**（按题）｜18/21 | 1 / 0 / 7 |
| `/ask` 取件（全 50 题） | 50 | 63 篇 | 90%（按篇） | **92%**（按篇，58/63） | 1 / 0 / 49 |
| coach 注入 | 15 | 15 篇 | 93% | **93%**（14/15） | 0 / 0 / 15 |

唯一变化的条目是「我之前哪些笔记提到过向量数据库」：2/3 → **3/3**（原来缺的那篇在笔记级排第 5 篇，正好卡在 5 篇上限之内，深召回后进来了）。

## 归因证据：排名一条未动

对 72 条查询逐条比对 before/after 快照：

- 「前 top-k 条分块去重后的笔记序」**0 条变化**；`hit / recall / precision_k / rank / top1_sim` 逐条相同。
- 检索层汇总：hit-rate **97%** ｜ MRR **0.913** ｜ recall@k **94%** ｜ precision@k **14%** —— 与基线**逐位相同**。
- 因此差异只能来自取件口径，不存在「检索顺便变好了/变差了」的混杂。这一条是本次数字可用的前提，不是锦上添花。

## 下一处瓶颈：取件上限（本版新发现，已量化）

同一批召回（平均 **24 条分块 = 13.8 篇笔记**；50 题里 **49 题**可用笔记数超过 5 篇上限）下，只改「交付几篇」：

| 交付上限 | cross_note 按题 | cross_note 按篇 | 全场景按题 | 平均交付 |
|--:|--:|--:|--:|--:|
| 3 篇 | 79% | 17/21 | 93% | 3.0 篇/题 |
| **5 篇（当前）** | **83%** | **18/21** | **93%** | 5.0 篇/题 |
| 8 篇 | 90% | 19/21 | 96% | 7.9 篇/题 |
| 12 篇 | 100% | 21/21 | 98% | 11.5 篇/题 |
| 16 篇 | 100% | 21/21 | 98% | 13.5 篇/题 |

被上限切掉的 4 篇期望笔记，笔记级位次是 **#8 / #8 / #9 / #12**。**结论**：v1.4 把瓶颈判断为"召回深度不够"，实测修正为"**深度够、上限低**"——12 篇上限即可全覆盖，但代价是每次提问交给模型的材料从 5 篇涨到约 11.5 篇。这是**生成层的取舍**（材料更多是否真的答得更好、噪声是否抵消收益），留给生成层评测回答，不在检索层拍板。

## coach 侧：材料形态变了，怎么读「注入精确率」

注入精确率 78% → 67%，看着像退步，逐条看原因：

- 注入召回不变（14/15 篇期望笔记都注入到了），变化只是**多注入了 3 篇**（18 → 21）。
- 标注口径是「每条 coach 题只标 1 篇期望笔记」，所以任何多注入都会被记成"误注入"——精确率的分母天然不欢迎"多给材料"。
- 多注入的 3 篇逐条看：**2 篇是同主题相邻笔记**（问 Transformer 组件 → 追加「Transformer 三大架构变体对比」；问 Redis 数据结构选型 → 追加「数据结构设计反模式」），**1 篇是链接清单**（问 skill 加载机制 → 追加「claude-code 官方文档参考链接」）。
- 另一侧同时减少的是**同篇重复**：多题从"3 条同篇分块"变成"1 篇 1 条"。注入提示词按 `（来源：<笔记>）` 逐条渲染，旧口径下同一路径会出现 2~3 次——既重复占预算，也让模型看到更像"同一份材料被贴了三遍"。

**判断**：形态变化（同篇多块 → 多篇各一块）本身是对的（同一处口径错了两处），但"材料更宽是否更好"在检索层量不出来，属生成层问题。

## 已知边界与遗留

1. **上限（5 篇 / 3 篇）未动**：反事实显示它现在是主要约束，但它同时决定每次提问的模型输入体积与延迟——需要生成层证据，见上表。
2. **词表鸿沟**未动：fuzzy 两条漏召回（口语问法 vs 术语笔记）仍由 dense + BM25 双双落空，与取件口径无关。
3. **coach 注入精确率的口径**依赖「每题只标 1 篇期望」，要多注入了就必然掉——标注口径本身需要一次审查（是否该标"相关但不必需"的第二、第三篇）。
4. 期望集完备性审查仍未做。
5. 小样本：cross_note 只有 8 题 / 21 篇期望，±1 篇 = ±4.8pp；这类改动的结论应按下表看**逐条**变化，而不是只看聚合数。
