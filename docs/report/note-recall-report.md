# 差量提取召回改造报告（note 召回窗口）

> 日期：2026-10-05 ｜ 范围：note 管道第一步「召回已有笔记」——查询文本怎么取、召回多宽、怎么计数。
> 关联：[note-dedup-report.md](note-dedup-report.md)（合并确认的设计意图 + embedding 相似度的固有边界）、[note-sweep-async-report.md](note-sweep-async-report.md)（本管道跑在后台线程）
>
> **验证期间撞见一起索引事故**（embedding 模型换过、索引没重建，导致 6/8 技术检索失效），本报告里的数字全部是在修好之后重测的。事故本身见第三节末尾——它比这次改造重要。

## 一、问题

note 管道的职责是**差量提取**：只输出"已有笔记没覆盖"的新知识点。所以召回的完整性直接决定它能不能抑制住重复——**召回里没有的笔记，在提取眼里等于不存在**。

改造前的三步全都有问题，第四步是设计缺口：

| # | 问题 | 位置 | 实测（17 个真实批次，健康索引上重放旧方案） |
|---|------|------|------|
| P1 | 查询只取**批次开头** 1500 字 | `pipelines/note.py` | 17 个批次**没有一个** ≤1500 字；落在这次查询之外的字符占比 43% / 57% / 92%（min/中位/max） |
| P2 | `top_k=3` 数的是**分块**不是笔记 | `config.py` + `adapters/store.py` | 名义 3 条，51 个名额里**只有 33 篇不同的笔记** |
| P3 | 按笔记去重**失效** | `adapters/store.py` | 比较的两个 dict 键集不同（一个有 `similarity` 键、一个没有）→ 相等判断永假 → 同一篇的多个分块各占一个名额：51 个名额里 **18 个（35%）**是重复占用 |
| P4 | 召回**没有相似度下限** | `adapters/store.py` | 设计上会让不相关笔记进提取上下文。注意：**本次语料没能证明它出过问题**——健康索引上旧方案 51 个召回里没有一个 <0.4。这一条是设计缺口，不是实测故障 |

**P1 的实际代价（同一份健康索引上重放旧方案 vs 新方案）**：旧方案**漏掉 36 篇**本该召回的笔记，余弦 0.530–0.946——包括 0.946 的选型横向对比、0.840 的切片机制这种强相关笔记。这些笔记在提取眼里不存在，于是它们覆盖的内容会被当新知识重提。

### 语料

数据来自本机 LangGraph checkpoint 库里 `memory_sweep_inflight` 的真实批次快照（= 当时真正喂给 note 管道的原文）：4 个会话线程、**17 个真实 fire 批次**、60 个用户回合。

- 批次字符数 min / 中位 / max：**2634 / 3522 / 18128**；用户回合 2 / 3 / 7；
- 助手讲解 60 条，长度中位 **1142** 字、最长 3162 字（22 条超过 1500 字）；
- 用户消息 60 条，长度中位 **17** 字（超过 200 字的只有 5 条）。

**失败方向**：欠抑制 → 重复笔记与闸门噪音。**反向风险**：上下文里塞太多不相关笔记会诱发过度抑制（模型倾向判"已覆盖" → 输出 `[]` → **静默丢内容，且不经过任何闸门**）。两个方向都要防，但代价不对称——重复是可见可修的，静默丢不是。

## 二、改造后

三件事：**按助手消息分组 → 消息太长就切开 → 逐块查一次，结果合并。**

### 1. 按助手消息分组

要提取成笔记的是**助手讲出来的知识点**；用户输入多半是贴回来的运行结果、报错或配置。所以一条助手消息算一组，用户消息只有在很短（≤200 字）时才跟着它并入同组——短回是主题信号（如"Context 和 useMemo 有什么区别？"），整条粘贴不进查询。

最初是按"助手消息 + 用户回复"合成一组，实测有一批 8 次查询里 **6 次花在一份 `--dump-config` 输出上**（该批 18128 字里讲解只有 2672 字、粘贴 15421 字），2672 字的讲解只占 1 次查询。改完之后：**58/58 条助手讲解在查询里有表示，5 条长用户消息 0 条进查询。**

### 2. 一条消息太长就切开

超过 1500 字的部分**不是丢掉，是切开——每一块单独查一次**（只取开头的话，后面的内容在查询里没有表示）。

切法沿用 RAG 那套分块逻辑（`domain/chunking.py`）：尽量切在段落边界，只有段落本身就超过 1500 字时才硬切；相邻两块留 100 字重叠，避免把一句话从中间切断。不超过 1500 字的短消息，它本身就是一块。

### 3. 每条消息的第一块一定会被查

一次沉淀最多发 8 次查询（8 × 1500 字 ≈ 12000 字，与差量正文的上限同量级）。名额这样分配：**先把每条消息的第一块占上**，剩下的名额再按顺序补给长消息后面的块——某条消息的第一块如果没发出去，这条消息在查询里就完全没有表示。曾用过"把全部块拉平了均匀取样"，实测正好跳过了某条讲解的第一块。

### 4. 合并结果

逐块检索后**按笔记路径归并、相似度取最大**（同一篇的多个分块从此只占一个名额，P2/P3 一并解决）；余弦低于 0.4 的丢掉；最后按**笔记篇数**截断（`top_k` 的语义从"分块条数"改为"笔记篇数"）。

### 参数与依据

| 参数 | 值 | 依据 |
|---|---|---|
| `NOTE_QUERY_CHARS` | 1500 | 单块的长度上限。**这个值是继承的**（改造前就写死 1500），不是推导出来的；站得住的理由是与提取正文的预算对齐（8 × 1500 = 12000 = `NOTE_CONTENT_CHARS`），且助手消息长度中位 1142 字、多数正好一块。**没有按检索目标（笔记分块 800 字）校准过**，见第五节 |
| `NOTE_RECALL_MAX_QUERIES` | 8 | 8 × 1500 = 12000 字，与差量正文上限同量级；实测每批 3–8 次，从不触顶 |
| `NOTE_RECALL_USER_MSG_CHARS` | 200 | 用户消息长度中位只有 17 字；超过它的仅 5 条（204×3、1625、15421），后两条是粘贴回来的运行结果 |
| `NOTE_RECALL_MIN_SEGMENT_CHARS` | 30 | 更短的一组是寒暄（"继续""懂了"），单独查一次只带回噪声 |
| `NOTE_RECALL_TOP_K` | **10** | 实测每批最多 **9 篇**相关笔记（修好索引后的读数），取 10 覆盖全部实测批次。上下文成本 10 篇 × 500 字 = 5000 字，相对 12000 字正文预算仍小 |
| `NOTE_RECALL_SIM_MIN` | 0.4 | **未定标**：健康索引上相关笔记的余弦最低 0.534，这个下限根本不触发；它上面有没有该挡的噪声、有没有把真相关的挡掉，现有数据答不了（见第五节） |
| `NOTE_CONTEXT_LIMIT` | 500 | 每篇已有笔记在提示词里的截断字数（沿用原有值） |

一次沉淀的代价是 3–8 次 embedding 调用（改造前是 1 次），跑在后台线程，与提取本身"几十秒"相比可忽略。

### 观测

新增 `note_recall` 审计事件（**只记路径与分数，不记正文**）：`tech` / `batch_chars` / `query_count` / `query_chars` / `query_truncated` / `kb_notes` / `sim_min` / `content_chars` / `content_truncated` / `recalled_count` / `recalled[{path, sim}]`；`sweep_fire` 补 `chars`（与触发判定共用同一把尺）。

`kb_notes` 必须和召回结果一起记：召回为空有两种成因——**库里本来就没有笔记**（正常），和**有笔记但都被下限滤掉了**。少了总数这两个状态分不开。

## 三、验证（同一批 17 个历史批次的回放）

回放直接调用改造后的生产函数（分组与切块也复用生产那两个函数，不另抄一份），对照的 oracle 是"同样的查询、同样的下限，**不设篇数上限**"。

### 改造前后（同一份健康索引，同一批批次）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 漏掉的相关笔记 | **36 篇**（余弦 0.530–0.946） | 0 篇（未覆盖 0/84 次查询） |
| 名额浪费（同篇占多个名额） | 51 个名额里 **18 个（35%）** | **0** |
| 每批召回篇数 | 名义 3 条（实际 ≤3 篇） | 3–10 篇，中位 8 |
| 召回到的余弦 | —— | min 0.534 / 中位 0.735 / max 0.946（**没有一条低于 0.5**） |
| 有相关笔记的批次 | —— | 17/17（每批最少 2 篇） |

剩下的 3 篇没进上下文：每批相关笔记最多 12 篇，上限 10 截掉了排在尾部的 3 篇（余弦 0.49 / 0.53 / 0.549，分布在 2 个批次）。这说明**"被截 = 0"不该作为目标**——只要候选比名额多，上限永远会截掉点什么；要问的是"截掉的是不是尾部弱相关的"（这次截掉的正好贴着 0.4 下限）。真要让它们也进来，该动的是下限而不是上限。

### 索引事故（验证期间发现，比这次改造重要）

回放第一轮出现一个无法解释的现象：5 个批次召回为空，而库里明明有讲同一批主题的笔记。追下去发现**索引里的向量来自两个不同的 embedding 模型**：

- `.env` 里 `EMBEDDING_MODEL=text-embedding-v4`，而 `config.py` 的默认值是 `text-embedding-v3`，索引是在 v3 时代建的；
- 把每块**存下来的向量**与**用当前模型重算同一段文本**对比，全库 884 块里约 **790 块**是旧空间（materials / reports 抽样 24 块全部不一致；knowledge 240 块里 167 块不一致）；
- 于是对这些块，查询向量与存量向量近正交（余弦 0.0–0.08，出现过 -0.06）。**6/8 个技术的笔记连自己的标题都查不回自己**（0.03 左右）。

**为什么没人发现**：① 重索引的跳过判据是 `content_hash = sha1(分块器版本 + 正文)`——**模型名不在里面**，换模型后旧块全被判成"内容没变，跳过"；② 该集合是 Chroma 的旧版配置建的，"模型变了会拒绝打开旧集合"那套保护没有生效，于是静默混用。

**修法**：`.env` 回到 v3（与代码默认值一致），对不一致的 7 个文件 / 73 块强制重嵌。修完 8 个技术的自查询余弦从 0.03 升到 **0.64–0.90**。

**影响范围**（不止笔记召回）：那些技术上 `find_note_match` 的语义去重退化成了"只认一模一样的标题"（候选余弦全在 0.03，被 0.4 下限全数跳过），`/ask` 的 RAG、coach 的 KB 注入、read 复用同样受影响。**这份报告第一版里"某技术的笔记确实不相关"的结论就是这么来的**——那些笔记其实是同一批主题，只是取不回来。

## 四、一个被否决的方案：小库短路

**提议**：库里笔记篇数 ≤ 取用上限时，跳过相似度下限，把全部笔记给出去。

**实现后又撤回**，理由：

1. **与管道自己的理由冲突**。上一步刚写死"给了不相关的笔记会诱发过抑制 → 输出 `[]` → 静默丢内容"，而这一条的辩护是"噪声不会诱发抑制"。同一件事两套标准，且后一套没有实测支撑。
2. **代价方向是反的**。它想防的后果是"上下文被清空 → 重提已覆盖内容" → 最坏是一篇**可见、可修**的重复笔记；它自己引入的后果可能是 `[]` → **静默、不可修**的内容丢失。仓库既有的取舍是"宁可可修的重复，也不静默错并"，这一票该投给下限。
3. 提出时还引用了一条数据（"60 个回合里 23 个没有任何 ≥0.4 的相关笔记，所以小库会拿到噪声"）——**这条数据随索引事故一起作废了**：修好索引后 84/84 个查询都有相关笔记。撤销的主论据（第 1、2 条）不受影响，但那条辅助论据不能再引用。

最终行为：**下限一律生效，不看库大小**。

## 五、遗留

- **下限 0.4 没有定标**（当前最重要的一条）：健康索引上它不触发（相关笔记最低 0.534），所以既没证据说它挡对了，也没证据说它挡错了。要判它，得先补一个读数——**被下限挡下的最高余弦**（现在只记过了下限的那几篇）。做法是把过滤从 `adapters/store.py` 挪到管道里，事件加一个字段；挪的时候注意**先按相似度过滤、再按篇数截断**，否则第 7 篇本来合格的笔记会被第 6 篇噪声挤掉。
- **查询块大小（1500）没有按检索目标校准过**：被检索的是 800 字一块的笔记分块，查询块却是 1500 字。查询比被检索的块长会稀释主题（一块讲了两个点，向量就是这两个点的平均），这是机制上的风险，但没测过。要测就按块 800 / 1500 / 3000 做 A/B，比召回集合与余弦分布。
- **索引护栏没做**：现在换一次 embedding 模型仍会静默混用（见第三节）。最小改法是分块元数据里记一个模型名字段，跳过判据改成"正文没变**且**模型没变"。
- **提示词里的一句话在"库里有笔记但都被滤掉"时不准确**：`_build_extraction_user` 此时输出"（本技术暂无已有笔记，正常提取全部知识点）"。要改需按 [PROMPT_DESIGN.md](../PROMPT_DESIGN.md) 走。
- **提取正文仍是取头截断 12000 字**：17 个真实批次只有 1 个触发（那条 15421 字的粘贴，恰好在末尾，讲解没被切到）。风险形状是真的——粘贴只要出现在讲解**前面**，讲解就整段被截掉。
- **hybrid 检索未用于此处**：[note-dedup-report.md](note-dedup-report.md) 附录实测的是**去重召回**场景（结论：净提升为零，且 RRF 分数破坏阈值语义），不覆盖差量上下文。要用必须按同款方法重测。
- **业务指标还没有**：重复提取率、静默重复入库数、`[]` 率看的是 LLM 行为，历史数据里没有。上限从 6 提到 10 会让上下文多塞笔记，`[]` 率正是这个改动的配套监控项。
- **上限从 6 提到 10 的依据是"每批最多 9 篇"**：这个上限的语义是"够覆盖就好"，不是越大越好——过抑制会静默丢内容，所以不要再往上加。

## 六、怎么验证

- **单测（零网络）**：`tests/test_note_recall.py` 17 例——按助手消息分组、粘贴不进查询、寒暄过滤、长消息切块、每组第一块必发、消息超上限时均匀取样、path 并集、下限过滤、回退判据（只在"一个候选都没有"时回退）、篇数截断、无分组时维持旧行为、后面的主题必须进上下文、库大小不改变下限；`tests/test_audit_events.py` 覆盖事件字段。
- **回放（花 embedding 调用，不花生成调用）**：用历史 fire 批次做输入，同时跑"生产实现"和"不设篇数上限的 oracle"，四个断言是"未覆盖 = 0、低于下限的召回 = 0、回退条目 = 0、生产漏掉的 = 0"。回放脚本未随仓库分发（含本机真实对话）。
- **索引健康检查（零成本，建议常用）**：拿一篇笔记自己的标题当查询，看能不能查回它自己——修好后余弦应在 0.6 以上；掉到 0.1 以下就说明索引的向量空间和当前模型对不上。
