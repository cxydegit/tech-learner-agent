# 混合检索：量化评估 + 两个修复的验证（56 条真实场景查询）v1.1

> **v1.1（本文）**：在 v1.0（`rag-hybrid-scenario-eval.md`，纯评估，发现 3 个问题）基础上，实施并验证了两个修复——分词点号不拆词、coach 注入门槛换分数并重标阈值。同时把检索窗口统一为生产真实的 top_k=8，并暴露了一个更深的新问题（片段灌水）。
> 数据说明：评测脚本未随仓库分发，下表为当时实测记录。

---

## 一句话结论

**混合检索值得用：搜专有名词的找对率比纯语义高两成，常规问答零牺牲、联想还更强。** 这轮又把它推进一步：分词修复让 `FT.SEARCH` 这类点号缩写能搜到了，coach 陪练的注入门槛从"形同虚设"变成"真的能拦"。**但把检索窗口改成生产真实值后，暴露了一个更深的问题：混合检索的融合是"按片段"排名的，长笔记的多个片段会把正确答案的单个片段挤出前 8——这是下一步要修的。**

---

## 测了什么

56 条查询按"用户会怎么问"分 6 类（每类回答一个具体问题）：

1. **直接搜专有名词**（14 条）——`RoPE`、`FlashAttention`、`Auto-tiering`…混合检索的设计初衷、纯语义的经典短板。
2. **常规概念问答**（10 条）——确认混合检索没把正常能力搞坏。
3. **跨笔记联想**（8 条）——"我之前哪些笔记提到过 X"，答案分散多篇。
4. **口语化/记错名**（10 条）——"对象存 string 是不是不好"这种，跟笔记标题对不上。
5. **分辨相近笔记**（8 条）——几篇概念重叠的笔记抢一个问题，该指向哪篇。
6. **笔记里没有的问题**（6 条）——测会不会"自信地"给个错答案。

指标说人话：**找对率**=相关笔记进没进前 8；**排名质量**=平均排第几（1.0=每次第一）；**联想找全率/噪声率**=联想场景相关笔记找全几成、混进几成噪音。

---

## 每类场景的表现（修复后的现状，窗口 top_k=8）

| 场景 | 纯语义 找对率/排名 | 混合 找对率/排名 | 说明 |
|---|---|---|---|
| 专有名词 | 57% / 0.333 | **79% / 0.732** | 混合救回 5 条纯语义找不到的（见下） |
| 常规问答 | 100% / 1.0 | 100% / 1.0 | 两路都好，零牺牲 |
| 跨笔记联想 | 100% / 1.0 | 100% / 1.0 | 找全率：纯语义 81% → **混合 92%** |
| 口语化 | 90% / 0.783 | 90% / 0.850 | 基本打平，混合排名略好 |
| 分辨相近 | 100% / 0.792 | 100% / 0.750 | 都能分辨主次，混合有一例排名差一档 |
| 笔记里没有 | 1/6 过闸 | **0/6 过闸** | 见"修复二"，阈值真能拦了 |

各场景一句话解读：

- **专有名词是主战场**：14 条里纯语义只对 8 条，混合对 11 条。混合救回了 `FT.SEARCH`（分词修复的成果）、`RediSearch`、`FlashAttention`、`vLLM` 这几条纯语义完全找不到的，还有 `HyperLogLog`、`createRoot`、`JSONPath` 等纯语义只排第三、被混合顶到第一的。**还有 3 条两路都找不到**（`RoPE`、`KV Cache`、`PagedAttention`）——这是下面"新发现"要讲的，不是分词能解决的。
- **常规问答零牺牲**，联想找全率还从 81% 提到 92%（问"哪些笔记提过 X"更不容易漏）。
- **口语化两路都 9/10**，唯一漏的是"ai 回复每次都不一样怎么办"（目标笔记在 redis 目录但内容讲 LLM 工程，跨库被挤掉），是真实用户会问的措辞，记一笔。
- **分辨相近**都能找到主笔记，但混合把"Transformer 内部结构"排在第二（被"架构变体"那篇的关键词抢分）。这类场景里前 8 名必然有 7 条其它笔记，"噪声率低"是测法自带，不代表检索差。

## 这轮修了什么、效果如何

### 修复一：分词——点号不再拆词（`FT.SEARCH` 能搜到了）

**问题**：BM25 把文本切成词再数权重，越罕见权重越高。`FT.SEARCH` 被点号拆成 `ft` + `search`，两个都是常见词、权重被稀释，关键词这路自己都找不准。

**改法**：`src/domain/hybrid.py` 的分词正则允许点号留在词内，`FT.SEARCH` 整体当一个罕见词 `ft.search`。

**效果**：实测 `FT.SEARCH` 从"两路都整篇丢失"变成混合检索排第 4（纯语义仍找不到）。顺带把 `HyperLogLog`、`createRoot`、`JSONPath` 等也顶到第一名。配套单测从断言"拆成 ft/search"改成"整体成词"，新增一条验证"含 FT.SEARCH 的文档独占高分"，全量 221 个测试通过。

> 诚实标注：**这是修了"点号缩写"这一类，不是全治好专有名词**。下面"新发现"说明为什么 `RoPE`、`PagedAttention` 仍找不到。

### 修复二：coach 陪练的注入门槛——换分数 + 重标阈值

**问题**：陪练每回合检索笔记，相似度 ≥0.5 才喂给大模型。但混合检索返回的相似度是"相对排名分"（第一名恒为 1.0），0.5 这个绝对门槛对它形同虚设——任何问题它第一名都 ≥0.5。实测 6 个"笔记里没有"的问题它全放行。

**改法（两步）**：
1. **换分数**：`src/pipelines/route.py` 的闸门改用融合时保留的真实余弦（`dense_similarity`），BM25 独有的命中（没有可标定分）宁可不注入。评估脚本的注入模拟同步成同一逻辑。
2. **重标阈值**：写了个标定脚本（未随仓库分发）统计正负样本分布——该注入的笔记余弦在 0.58~0.87，不该注入的 top-1 在 0.45~0.62。把阈值从 0.5 提到 **0.65**：正样本还保住 9/10，负样本误放行从 3/6 降到 **0/6**。

**效果**（coach 注入模拟，10 个陪练场景条目）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 注入精确率（注入的片段里多少是对的） | 混合 48% / 纯语义 59% | **混合 75% / 纯语义 82%** |
| 误注入（不该喂的喂了） | 混合 11 / 纯语义 7 | **混合 3 / 纯语义 2** |
| 负样本过闸 | 混合 6/6 / 纯语义 5/6 | **混合 0/6 / 纯语义 1/6** |

**结论**：coach 门槛从"形同虚设"变成"真能拦"。代价是注入召回从 100% 降到 90%（丢一条该注入的），换回误注入大幅下降——对"拿错笔记当依据"这个更伤人的错误来说，值得。

## 新发现（下一步要修的）：混合检索的"片段灌水"把正确答案挤走

把窗口改成生产真实值（top_k=8，候选池=24）后，`RoPE`、`PagedAttention` 反而找不到了——它们在旧的 top_k=5 窗口（候选池 15）下明明能排到第 2、第 3。

**根因**：混合检索的融合是按"片段"排名的，不是按"笔记"。一条长笔记的多个片段会同时出现在语义榜和关键词榜里，各拿一份融合分，把前 8 名占满。实测 `RoPE` 的正确答案笔记关键词排名第 1（BM25 完美命中），但它只有 1 个片段、只拿一份分；而 `rag-架构模式` 一篇就占了前 8 名里的 3 个片段。**正确答案的单片段被长笔记的多片段挤出去了。**

**这意味着**：
- 不是分词能修的（`RoPE` 本来就是罕见整词，BM25 已经排第一了）。
- 真实 `/ask` 用 top_k=8，所以这个问题在线上真的会发生——用户搜 `RoPE`，答案里没有 transformer 那篇。
- 融合结果对候选池大小敏感（非单调），这本身就不够稳。

**修复思路**：让融合后的前 k 名做"笔记多样性"——同一篇笔记只保留它融合分最高的那个片段，凑够 k 篇不同笔记再截断。这样长笔记占不满前 8，正确答案的单片段有位置。**代价要想清楚**：一篇笔记的"深度"从 3 个片段变 1 个，回答时同一来源的素材变薄，但能覆盖更多笔记——对"联想检索"（多篇）更友好，对"深挖单篇"可能略降——这是一个需要权衡的取舍。

---

## 建议（按优先级）

1. **"片段灌水"修复**（新发现，当时未实施）：做法是先加笔记多样性，再重跑评估确认专有名词和联想都受益。但它改的是检索核心、影响 `/ask` 全局，需谨慎评估。
2. **`KV Cache` 仍是死角**：`kv` 撞上"KV 存储选型"那篇、`cache` 烂大街，分词和融合都难救，得靠"词组相邻"这种更重的信号。可以长期搁置。
3. **回归看板**：以后改检索/切词/阈值，都跑一遍 `--retriever both`，重点盯专有名词和 coach 注入两栏。
