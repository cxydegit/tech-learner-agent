## 一、P0 检索评估体系：为什么先建尺子

**背景**：`/ask` 问答上线后，检索质量从"后台缺陷"变成用户可感知的"答非所问"。但当时去重阈值 0.55、缓存阈值 0.62、chunker v2 这些决策**全是拍脑袋**——没有任何数据能回答"检索到底好不好"。

**目标与约束**：零新依赖、**不改任何 `src/` 源码**、产出可复跑的评估基线。

**交付**（两个新文件）：
- `eval_golden.json`：基于真实语料的黄金集——`retrieval` 20 条（12 条单篇命中 + 8 条跨笔记综合，覆盖全部 12 篇现有笔记）、`dedup` 10 条（5 应合并 + 5 不应合并）、`read_cache` 5 条（3 命中真实报告 URL + 2 不存在）
- `eval_retrieval.py`：一条命令跑三维度——检索 `hit-rate@k` + `MRR@k`；去重合并精确率/召回率/误合并/漏合并/错合并；缓存精度。带 `--check`（零费用校验黄金集）与 `--out`（markdown 落盘基线）

**首轮基线**（真实 embedding 评估）：

| 维度 | 指标 | 结果 |
|---|---|---|
| 检索（20 条） | hit-rate@6 / MRR@6 | **100%** / **0.852** |
| 去重（10 条） | 合并精确率 / 召回率 | **62%** / 100% |
| | 误合并率 | **60%**（3/5 不应合并被合并）← 0.55 阈值过松的实证 |
| 缓存（5 条） | 精度 | 100% |

**过程中的三个修复**：
1. **指标口径 bug**：`summarize_dedup` 的「正确」把「正确合并」和「正确不合并」混在一起，抬高召回/精确率分子——改为合并类指标只统计应合并样本（cm/cn/wm/fm/mm 分列）。
2. **索引过期**：redis.io 的 3 份报告从未进索引（索引里只有 4/7 份报告 URL）→ 缓存漏命中是索引过期而非代码问题。跑增量索引 +23 个文件修复。**这正好佐证了 P3 索引对账的价值**。
3. **黄金集标注错误**：「哪些笔记讲到了向量搜索？」期望的 redis 五大核心角色笔记根本没进 top-8（它只在角色列表里顺带提了句"向量数据库"），语义上最相关的是 rag VectorStore 笔记（0.61 排第一）——**系统行为是对的，标注错了**，修正 expected。

## 二、P0 的五个盲点：为什么 100% 是假象

首轮 100% / 0.852 看起来无可挑剔，但用户正确地质疑"纯 dense 对当前语料足够 → 还有必要做 P1 吗"。拆开看，这套指标测的是分布的「容易段」，盲点恰好是 P1 想补的场景：

1. **语料太小，top_k 近乎"全覆盖"而非"判别"**：每 tech 才 6 篇笔记，top_k=5/8 把候选池扫了大半。在 6 篇里排前 5 和在一千篇里排前 5，是两个量级的任务。黄金集几乎没有近重复干扰项。
2. **query 是"知道答案的人"写的**：干净、对题，测出来是**上界**，不是真实 `/ask` 分布（含糊、记错名、跨领域、用笔记里没有的词）。
3. **只测召回，不测精度**：指标只问"期望笔记在不在 top-k"，不问"top-k 里有多少噪声"——正确答案埋在 7 条无关结果里照样满分。**"如何防止 RAG 幻觉"那条在 12 篇语料里仍被挤到 rank 5 就是信号**。
4. **黄金集没有任何"精确词/专有名词"用例**：RedisJSON、FT.SEARCH、缓存穿透这类词正是 dense 的经典弱点，但 20 条 query 一个都没测到——**P1 想补的短板，根本没被测量**。
5. **顺带提及的判别问题**：一篇"顺带提到概念"的笔记 vs 一篇"整篇都在讲概念"的笔记，dense 会把后者顶上来、把前者挤出 top-k。

## 三、hard 用例探针与定稿

用户质疑"12 篇笔记构造不出 hard 用例"。回应：12 篇确实构造不出"近重复干扰判别"类 hard，但**精确词类 hard 在这个规模就是可测的**，而且是 P1 文档自己点名的失败场景。直接探针实测（判别信号不是 hit-rate，而是 **rank**）：

| query | 含该词的笔记（词法 ground truth） | dense 检索到它的位置 |
|---|---|---|
| `FT.SEARCH` | 仅 redis-stack 一篇 | **未进 top-8** ❌ |
| `RediSearch` | 仅 redis-stack 一篇 | **未进 top-8** ❌ |
| `缓存穿透` | 仅概率数据类型一篇 | rank 7（埋在 6 条无关下）⚠️ |
| `RedisJSON` | redis-stack + 五大核心角色 | rank 6 / rank 1 ⚠️ |
| `分布式锁` | 仅基础数据类型选型决策一篇 | rank 1 ✅ |

**结论**：精确词/顺带提及类 hard 在 12 篇语料里就能真咬人——5 条里 2 条整篇丢失（FT.SEARCH、RediSearch，dense 返回的全是"看似相关"的 RAG/Redis 干扰项）。这解释了为什么之前 100% 没暴露它：query 选择偏差 + hit-rate@k 对 rank 6-7 太宽容。

**定稿**：5 条 hard 进黄金集（`FT.SEARCH` / `RediSearch` / `缓存穿透` / `RedisJSON` / `分布式锁`，最后一条作回归守卫）。

## 四、P1 混合检索实施

**设计**（6 处文件改动）：

| 文件 | 改动 |
|---|---|
| `src/domain/hybrid.py` **新增** | 纯函数：`build_bm25`（标准库自实现 **Okapi BM25**，k1=1.2 / b=0.75）+ `rrf_fuse`（**RRF 名次融合**，按 id 去重、保留 `dense_similarity`/`bm25_score` 供下游） |
| `tests/test_hybrid.py` **新增** | 10 条单测：BM25 排序/精确词/空输入、RRF 融合/去重/归一化 |
| `src/adapters/vector.py` | `keyword_search_knowledge`（collection 全量 BM25 top-k）+ `hybrid_search_knowledge`（dense+BM25 → RRF，每路取 3× 候选、任一空回退另一路） |
| `src/pipelines/qa.py` | `_search_notes` 改走 hybrid，异常回退纯 dense |
| `src/config.py` | `QA_USE_HYBRID`（默认 true，可关回纯 dense）、`QA_RRF_K`（默认 60） |
| `eval_golden.json` / `eval_retrieval.py` | 检索集 +5 条 hard；`--retriever dense/hybrid/both` 对比 + hard/常规分集 |

**验收结果**（25 条黄金集，dense vs hybrid）：

| 指标 | dense | hybrid |
|---|---|---|
| hit-rate | 92%（25 中 23） | **100%**（25 中 25） |
| MRR | 0.734 | **0.851** |
| hard 集 hit-rate | 60%（MRR 0.262） | **100%**（MRR 0.607） |

5 条 hard 全修复：`FT.SEARCH` ✗→✓5、`RediSearch` ✗→**✓1**、`缓存穿透` ✓7→✓3、`RedisJSON` ✓6→✓2、`分布式锁` ✓1 保持（回归守卫）。常规集 MRR 0.852→0.912（"防幻觉"那条 rank5→2）。

**验收结论**：P1 有据可依——dense hard 集只有 60% 证明"12 篇语料够用"的判断是错的；hybrid 把精确词短板补上，且常规集不降反升。**/ask 真实路径冒烟**：`FT.SEARCH 是什么` 在 `_search_notes → hybrid → 分组` 链路下 redis-stack rank 1 进回答分组（dense 原本整篇丢失）。

**单测**：hybrid 10/10；全量 **88/88** 通过（qa 改动无回归，I1 也过）。

## 五、去重确认层 v1（P0 去重部分，后被压力测试揭穿）

**病根**：`find_note_match` 的 `similarity >= 0.55` **一个数字同时干两件事**——"值不值得考虑"和"该不该合并"。但 embedding 相似度测的是"相关度"，不是"是否同一知识点"。高相似但无关 = 相关度够高、同一性为零。两条分布的尾巴重叠（实测 0.66 误合并 vs 0.69 正确合并），怎么调阈值都伤一头。

**方案**：把「候选召回」和「合并决策」解耦——
- 召回放宽（保 recall）：语义 **top_k=2**（原来只取 top1，太窄），阈值不调
- 决策收紧（保 precision）：独立确认层 `_same_knowledge_point`，信号优先级 **标题 overlap > 具体标签 overlap > 内容判别性概念 containment**，任一确认 → `same`
- 都不确认 → 独立新笔记（宁可可修的重复，不静默错并）
- `note_pipeline` 把新点的 `body` + `tags` 喂进 `find_note_match`（原来信号饿死在签名上）
- **元标签停用表**（踩坑/部署/最佳实践…）：堵"共享个 `#部署` 就误认"的坑（windows 笔记 #部署 让「Docker 部署 Redis 集群」误并入）

**黄金集表现**（12 条）：精确率 62%→**100%**、误合并率 60%→**0%**、召回率保持 100%。信号分布：7 应合并 = 2 标题 + 2 具体标签 + 3 内容；5 不应合并全 no（含 3 个高相似误合并 0.62/0.66/0.64）。单测 97 passed（新增 22）。

> ⚠️ **诚实标注**：这里"100%"后来被压力测试揭穿。当时我往黄金集塞了 3 条"措辞不同但同一件事"用例并给它们补了正文，然后内容信号把它们救回来——这等于"用例需要它，所以它必要"，**是循环论证**，不是"数据说值才开"。内容信号对"最初要修的问题"（那 3 个高相似误合并）其实没贡献，标题+标签就全拦下了。

## 六、压力测试：真正的 100% 是假的（fork 前最后的结论）

用户质疑"不能直接判定新方案 100% 准确"。承认三个结构性偏差：
1. **作者偏差**：代码我写的、黄金集我标的，甚至中间改过黄金集去迁就代码（改「向量搜索」期望、给「Stack 模块」补正文）——"我出题我答题"。
2. **样本太小**：rule of three（N 次 0 失败，95% 上限 ≈ 3/N）——误合并率 0/5 → 上限 **60%**（正好是旧方案水平！）；漏合并 0/7 → 43%；整体 0/12 → 25%。这套数据连"新方案确实比旧方案好"都只算弱证据。
3. **判定本身主观**：「Redis Stack 的模块组成」算不算和「redis stack 与核心版本差异」同一知识点，换标注者可能不同。

**对策**：LLM 合成压力测试（生成者 ≠ 标注者，去掉作者偏差）——对每篇真实笔记生成同义改写（措辞完全不同，应合并）+ 近邻干扰（相邻但不同，不应合并），规则程序化标注。生成 55 条（改写 47 / 近邻 8）。

**结果**（旧确认层 v1）：

| 指标 | 数值 | 分布 |
|---|---|---|
| 合并精确率 | **21%** | 正确合并 4 / 错合并 12 / 误合并 3 |
| 合并召回率 | **9%** | 正确合并 4 / 漏合并 31 |
| 误合并率 | **38%** | 8 条近邻中误并 3 |
| 漏合并率 | **66%** | 47 条改写中漏并 31 |

**根因隔离**（假设源笔记就是候选，零 embedding，只算确认层三信号）：

```
改写 47 条：标题确认 0 / 标签确认 4 / 内容确认 0 / 任一确认 4（9%），全不确认 43（91%）
```

三个致命真相：
1. **内容信号对"真正措辞不同"失效**：containment 要求改写的概念逐字出现在源笔记正文，真正重写的内容词汇全换 → 0/47。黄金集里"有效"是因为我写的正文复述了源笔记措辞（假阳性）。
2. **标题信号造成错合并**：「NoSQL内存数据库五种核心角色」带"五"，标题 overlap 撞「redis 的五大核心角色」（单字切分 + 0.4 阈值）。
3. **语义相似度分不开**：改写对源 0.50~0.75，近邻干扰也有 0.60~0.63——分布重叠，纯阈值无解。

**架构级结论**（引出 fork 后的新方案）：**交互层本来就是 precision 门**（match 送 `merge_candidates` 由用户确认），确认层却把 precision 门提前塞进 `find_note_match`，导致该让用户看到的候选根本没送出去 → 漏合并 66%。正确分工：`find_note_match` 只做 recall 导向（宁可多给候选），precision 交给用户确认 + LLM 判定。**确定性规则做不了语义等价判断——这就是 fork 后实施 LLM 判定方案（`docs/report/note-dedup-report.md`）的起点。**
