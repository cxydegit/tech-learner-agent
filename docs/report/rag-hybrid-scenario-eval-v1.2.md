## 一句话结论

**三个修复落地后，混合检索在 50 条真实场景查询里找对 49 条（98%），专有名词场景 14/14 全中。** 前面两轮（分词点号不拆、coach 门槛重标定）解决的是"精确词搜不到"和"陪练喂错依据"；第三轮挖出的才是真正的大头——一个让无关笔记白拿融合分的 bug，修掉后专有名词找对率从 79% 直接到 100%。

## 修正记录：v1.1 的"片段灌水"诊断是错的

v1.1 把"`RoPE` 的正确答案掉出前 8"归因于"长笔记多块灌满前 8"。**这是错的**——经核对，`rag-架构模式` 根本没有提过 RoPE/位置编码，真实原因是 `keyword_search_knowledge` 的一个 bug：

**BM25 对 `RoPE` 只找到 1 条真命中（transformer 笔记，分 2.87），但为了凑满返回条数，把其余 23 条 BM25 得分为 0（和查询毫无共同词）的块也当作填充返回了。RRF 融合按"在榜单里的排名"给每条加分，这 23 条 0 分填充块就按它们随便排到的位置（第 2~24 名）白拿了融合分。**

```
rag-架构模式::0 = 语义榜第1(1/61=0.0164) + 0分填充"关键词榜第12名"(1/72=0.0139) = 0.0303 → 排第一
transformer 笔记  = 关键词榜真正第1(1/61=0.0164)                                = 0.0164 → 第12名，掉出前8
```

**修复**（`src/adapters/vector.py::keyword_search_knowledge`）：只返回 BM25 分 > 0 的块，0 分填充块不进 RRF。改动三行，全量 221 个单测无回归。

**效果**（真实代码路径验证）：

| 专有名词 | 修复前（hybrid） | 修复后（hybrid） |
|---|---|---|
| RoPE | 掉出前 8 | **第 2 名** |
| FT.SEARCH | 第 4 名 | **第 1 名** |
| PagedAttention | 掉出前 8 | **第 2 名** |
| KV Cache | 掉出前 8（曾判为"真死角"） | **第 3 名** |

> 顺带说明：之前报的"结果随 top_k 抖动"（top_k=5 能找到、top_k=8 反而丢）也是这个 bug 的症状——候选池越大，0 分填充越多，污染越重。修掉后抖动消失。

## 当前完整数字（三个修复全生效，窗口 top_k=8）

| 场景 | 纯语义 找对率/排名 | 混合 找对率/排名 | 说明 |
|---|---|---|---|
| 专有名词 | 57% / 0.333 | **100% / 0.881** | 14/14 全中，多数第 1-2 名 |
| 常规问答 | 100% / 1.0 | 100% / 1.0 | 零牺牲 |
| 跨笔记联想 | 100% / 1.0 | 100% / 1.0 | 找全率 81% → **92%** |
| 口语化 | 90% / 0.783 | 90% / 0.850 | 两路都差同一条 |
| 分辨相近 | 100% / 0.792 | 100% / 0.750 | 混合一例排名差一档 |
| 笔记里没有 | 1/6 过闸 | **0/6 过闸** | coach 门槛修复的成果 |

**整体**：纯语义 86% / MRR 0.737；混合 **98% / MRR 0.897**（50 条里只差 1 条）。

### 三个修复回顾

1. **分词点号不拆**（`src/domain/hybrid.py`）：`FT.SEARCH` 整体当一个词，专有名词能搜到。
2. **coach 注入门槛换分数 + 重标阈值**（`src/pipelines/route.py` + `src/config.py`）：0.5→0.65，误注入从 3/6 → **0/6**，注入精确率混合 48%→75%。详见 v1.1。
3. **零分填充过滤**（`src/adapters/vector.py`）：本轮，专有名词 79%→100%。

## 剩余的已知弱项（诚实标注）

1. **口语化唯一漏网**：`ai 回复每次都不一样怎么办` 两路都 miss——目标笔记在 redis 目录但内容纯 LLM 工程（温度参数坑），跨库检索被更"像 LLM"的笔记挤掉。真实用户会这么问，记一笔。
2. **裸缩写的 dense 噪声仍在**：即便修完 bug，`RoPE` 查询里 `rag-架构模式` 仍是语义榜第 1（内容无关，纯 embedding 对 3 字母缩写匹配差），权重无差别的 RRF 让正确笔记排第 2 而不是第 1。**这不影响召回（答案已含正确笔记），只影响排名精度**——真要压过它需要 reranker（cross-encoder）或对精确词场景给关键词榜加权，属 backlog，等语料变大或精度需求上来再做。

## 建议

1. **把场景评估纳入日常回归**：改检索/切词/阈值后跑 `--retriever both`，重点盯专有名词和 coach 注入两栏。
2. **reranker 记入 backlog**（上述弱项 2），当前 22 篇语料不值当引入新模型。
3. **保留教训**：`keyword_search_knowledge` 的"零分填充"是"为凑数返回"的隐性 bug 典型——检索层返回的内容必须真的命中才算数。
