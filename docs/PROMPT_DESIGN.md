# 提示词优化思路（Prompt Design Guidelines）

> **适用范围**：**设计或修改任何新提示词前必须阅读本文档**。
> **来源**：Note 模块（差量提取）的提示词实战经验沉淀——把踩过的坑固化成可复用的写法，以及"怎么验证改对了"。

---

## 一、Step 3 为什么重写提示词（背景：先看症状）

旧 `EXTRACT_SYSTEM_PROMPT` 硬性要求每条笔记必须含 6 小节：`## 是什么 / ## 为什么重要 / ## 通俗类比 / ## 代码示例 / ## 注意事项 / ## 参考资料`。两个致命后果：

1. **逼 LLM 重复**：无论输入多相似，都被要求"从头到尾重写全套" → 内容必然与旧笔记重复；
2. **逼 LLM 说废话**：内容不够时用套话填充——实证：知识库某笔记的"注意事项"是"分块过大会导致检索精度下降"这种放之四海皆准的话，"代码示例"直接写"无。"。

**结论：模板的错，不是模型的错。** 提示词把模型锁死在一个僵硬结构里，模型就交还僵硬输出。

---

## 二、核心思想（好的提示词好在什么地方？新提示词要参考这些设计：）


###  1：让模型只做它擅长的事，其余交给代码
时间 / 文件路径 / ID / 计数 / 相似度阈值等**确定性信息一律由代码生成并注入**，绝不交给模型生成。
- 反例（Step 1 教训）：collect/dig/read 提示词让 LLM 填"生成时间"占位符 → LLM 编造历史日期（`2025-09-02`、`2024年5月22日`），污染全部已生成文件。
- 自查信号：**新提示词里出现"日期 / 文件名 / 数量"字样 = 危险信号**，改为代码侧生成。

###  2：输出结构最小化 + 严格约束
- JSON 只保留必要字段（Step 3 为 `topic/tags/content` 三个），字段越少，LLM 越不会跑偏、解析越稳。
- 输出约束要具体到字符串级别："**只输出 JSON 数组，不要 ```json 围栏、不要前言、不要解释**"。
- 解析统一复用 `domain/extraction.py`（`parse_entries`），不要自造解析器。

###  3：质量门槛显式化（宁可少记、写透）
对"什么才值得产出"给出**可判定的标准**，而不是抽象的"要高质量"：
- Step 3 示范：一条笔记要有实际信息量——"能讲清楚 是什么/为什么/怎么用/关键细节 中的至少两点，或带一个可运行的例子"；"空洞的一句话概括、套话、常识性废话不要输出"；"宁可输出 2 条扎实的，不要 5 条空泛的"。

###  4：负面指令要点名具体模板
"不要模板化"这类泛泛禁令无效。要**点名具体的禁用字符串**：
- Step 3 示范："**绝对不要用 `## 是什么` `## 为什么重要` `## 通俗类比` `## 注意事项` 这种模板式小标题**"。

###  5：给正例，不给抽象
在提示词里放 1 个"好产出的样子"（Step 3 放了一段"好笔记的样子"：用贴切内容的小标题 `## 四种检索模式` 组织，每条写清是什么/适用场景/关键点）。
- 模型模仿正例，比理解抽象规则可靠得多。正例必须是真实"好"的，否则会照抄瑕疵。

> 使用说明：**参考思想，而不是照搬。** 以上的正面指导仅针对 Step 3 的笔记模块，不一定适合所有模块的内容。
> 项目硬约束：**涉及修改提示词的改动，改前先让用户审核新提示词质量，确认后再落地**——提示词是面向用户的行为契约，改动必须可 diff、可回溯。
